## 1. IOD modules (PS3.3 A.32.8.3, Table A.32.8-1)

Equipment: General Equipment C.7.5.1 M; Enhanced General Equipment C.7.5.2 M
Acquisition: General Acquisition C.7.10.1 M
Multi-Resolution Pyramid C.7.11.1 U

SOP Common C.12.1 M; Common Instance Reference C.12.2 M; Frame Extraction C.12.3 C.
There is no separate "Device" module in this IOD. UDI Sequence lives in General Equipment (UDI Macro, PS3.3 10.29). The Multi-Resolution Navigation module is retired.
A.32.8.3.1.1 constrains Optical Path code sequences: Illuminator Type CID 8125; Illumination Color CID 8122; Illumination Type CID 8123; Lenses CID 8121; Light/Image Path Filter Stacks CID 8124; Channel Description CID 8122.

Class legend: SLIDE = fact fixed at scan about slide/scan/scanner, identifies no individual by itself; PATIENT = identifies or is linked to an individual (route to HL7/FHIR); AMBIGUOUS = see reason.
PS3.15 column = Basic Profile action in Table E.1-1 (X remove, Z zero-length, D dummy, U new UID, K keep, C clean; "X/Z/D" = remove, or zero, or dummy depending on Type) + options that retain/clean. "not listed" = the attribute does not appear in Table E.1-1, i.e. the Basic Profile does not alter it.

Enhanced General Equipment: "a subset of the General Equipment Module with all Attributes changed to Type 1"; it overrides the type in General Equipment; meant to identify the system that produces the data, not the encoding toolkit. ## 4. UDI
**(0018,100A) UDI Sequence**, SQ, VM 1, type 3 in General Equipment (PS3.3 C.7.5.1): "UDI(s) of the entire equipment; one or more items", each item = UDI Macro (PS3.3 Table 10.29-1): **Unique Device Identifier (0018,1009) UT, type 1**: "full Human Readable Form of the UDI as defined by the Issuing Agency"; **Device Description (0050,0020) LO, type 3**: free text to distinguish items. Section 10.29.1: "The UDI is a combination of the Device Identifier and the Production Identifier"; format set by issuing agency (GS1, HIBCC, ICCBBA named); FDA requires the ISO/IEC 646 invariant character set; DICOM sets no length limit.
**There are no separate DICOM attributes named "Device Identifier" or "Issuer of UDI"** (PS3.6 string search over all non-retired rows: only (0018,1009), (0018,100A), (0050,0020), (0050,0021 Long Device Description), (0018,100B), (0018,1002) and RT (3010,0043) Manufacturer's Device Identifier ST). The issuer is implicit in the string's format (GS1/HIBCC/ICCBBA) and must be parsed out. This corrects the assumption in the brief (DI and Issuer as items of the sequence).
**FDA rule** (https://www.ecfr.gov/api/renderer/v1/content/enhanced/current/title-21?part=830&section=830.3, read 2026-11-24): "Unique device identifier (UDI) means an identifier that adequately identifies a device through its distribution and use by meeting the requirements of 830.20. A UDI is composed of: (1) a device identifier, a mandatory, fixed portion of a UDI that identifies the specific version or model of a device and the labeler of that device; and (2) a production identifier, a conditional, variable portion of a UDI that identifies one or more of the following when included on the label of the device: (i) the lot or batch within which a device was manufactured; (ii) the serial number of a specific device; (iii) the expiration date of a specific device; (iv) the date a specific device was manufactured; (v) for an HCT/P regulated as a device, the distinct identification code required by 1271.290(c)." "Version or model" = "all devices that have specifications, performance, size, and composition, within limits set by the labeler." 21 CFR 801.20(a): the label and package of every medical device shall bear a UDI. 830.20: UDI must be issued under a system operated by FDA or an FDA-accredited issuing agency and conform to ISO/IEC 15459-2, -4, -6 and the ISO/IEC 646 invariant character set. FDA UDI Basics (https://www.fda.gov/medical-devices/unique-device-identification-system-udi-system/udi-basics): serial numbers are part of the PI, only when the labeler puts them on the label; "GUDID does not include the production identifier (PI)."
**Conclusion:** a UDI identifies a model (the DI) and, only if the label carries a PI element, a specific lot or an individual device (serial) or manufacture date. Whether a given scanner's UDI string identifies an instance depends on whether it includes a PI serial/lot; DICOM stores the whole string, so a full UDI can contain the serial. Safe split for I2S: DI portion = model-level (SLIDE-like, like Manufacturer/Model); PI portion = instance-level (like DeviceSerialNumber). *(Parsing the DI vs PI out of a GS1/HIBCC/ICCBBA string requires the issuer's rules; not researched here: to confirm.)* Also note a scanner is a Class I/II device whose UDI may be absent (Type 3 in DICOM); the UDI also does not identify a slide or patient.

SLIDE (physical slide / scan facts; identify no person; none removed by PS3.15 Basic Profile except where noted):

- Specimen: SpecimenTypeCodeSequence, SpecimenLocalizationContentItemSequence, coded items of SpecimenPreparationSequence (Processing type 111701, Staining 127790008 + Using substance 424361007 CID 8112, Tissue Fixative 430864009 CID 8114, Embedding medium 430863003 CID 8115, Processing step CID 8113, Sampling Method CID 8110, Specimen Collection CID 8109)

- Optical Path: all items except OpticalPathDescription (OpticalPathIdentifier, IlluminatorType, IlluminationWaveLength/Color/Type, Light/Image path filters, LensesCodeSequence, CondenserLensPower, ObjectiveLensPower, ObjectiveLensNumericalAperture, ChannelDescription, PaletteColorLUT, ICCProfile, ColorSpace)
- Equipment: Manufacturer, ManufacturerModelName, SoftwareVersions, SpatialResolution, Modality (SM)
AMBIGUOUS (with reason):
- AccessionNumber: DICOM lists it as department IS "Imaging Service Request" number, Z in the Basic Profile with no retain option. It is a lab-system case key that links to a patient: I classify it PATIENT unless Ryan wants it as a slide-level opaque key (reason to keep: it is assigned per case, not per person; reason to drop: PS3.15 never retains it). Decision needed.
- ContainerIdentifier, SpecimenIdentifier, Issuer sequences, AlternateContainerIdentifierSequence, BarcodeValue, LabelText, SpecimenUID: they identify the physical slide, but are lab-assigned keys and often equal accession-derived or printed patient text (BarcodeValue "may be the same as Container Identifier"); PS3.15 D/Z/X; SpecimenUID is U (replaced unless Retain UIDs). Treat as opaque slide keys only if the lab confirms they carry no patient data.
- AcquisitionDateTime (and Study/Series/Content Date and Time, ProcessingDateTime 111702, SamplingDateTime 111469): the scan moment is a fixed fact about the slide, but DICOM treats dates as re-identification risk (Z/X; retained only via the Longitudinal Full Dates option; "modified dates" option exists). Decision: full-date SLIDE vs coarsened.
- DeviceSerialNumber, UDISequence/UniqueDeviceIdentifier (with PI), DeviceUID, StationName, GantryID, DateOfManufacture/Installation/Calibration: identify a scanner instance; DICOM removes them in the Basic Profile unless Retain Device Identity; they identify no person but can narrow a site. UDI: model-level DI = SLIDE, PI serial = instance-level.
- Institution Name/Address/Code/Department: institution identity, K only under Retain Institution Identity; I treat as provenance to be routed with the clinical stream, not slide.
- Free-text: ContainerDescription, ContainerComponentDescription, SpecimenShortDescription, SpecimenDetailedDescription, OpticalPathDescription, AcquisitionDeviceProcessingDescription, StudyDescription, SeriesDescription, ProtocolName, AcquisitionContextDescription, DeviceDescription, text "Using substance"/step description: free text can carry names (Clean Desc option C). Use the coded counterpart only.
- AcquisitionContextSequence: unconstrained items; Clean Structured Content C.
- ContainerComponentID: lot/version for a component but X.
- PrimaryAnatomicStructure, BodyPartExamined, Laterality: clinical anatomy of the patient's tissue; not identifying but clinical (CID 8134).
- ICCProfile: binary; content is device color characterization; may carry vendor/device text *(to confirm)*.
- UID attributes (StudyInstanceUID, SeriesInstanceUID, Frame of Reference UID, Device UID, Class UID): structural; DICOM replaces them (U); Manufacturer's Device Class UID is a class not instance identifier.
- Clinical Trial Sponsor/Protocol/Site/Coordinating Center/Time Point: trial context, not slide facts.
PATIENT: Patient module; Clinical Trial Subject/Subject Reading ID; referring/consulting/reading/performing physicians, operators; Accession Number (proposed).
